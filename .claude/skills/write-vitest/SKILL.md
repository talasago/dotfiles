# write-vitest

Vitest固有のテスト実装ルール。共通のテスト設計方針は`/write-test`を参照する。

## テスト構造

- `describe`・`it`ブロックでテストを構造化する
- `describe`にはテスト対象のクラス名・機能名・メソッド名を記述する
- 前提条件は`describe`のネストで表現し、`when`または`if`から始まる文で記述する
- 条件が3パターン以上になる場合は`it.each`または`describe.each`を使用する

## テストの要否判断（過剰なテストを作らないために）

新しいテストケースを追加する前に「このテストが検出する不具合を見逃したら、誰かが実際に困るか」を自問する。

- 実害が大きい傾向：主要な操作導線を止めうる条件分岐、認証・決済・データ永続化・外部送信
- 実害が小さい傾向：見た目・装飾的な属性、コピー・文言の内容そのもの、条件分岐・状態・計算を一切持たない静的な表示専用コンポーネント（型チェックとコードレビューで欠落・誤字を検出できる）

文言の存在自体を確認する価値があると判断した場合も、長文の完全一致（`getByText`への文章まるごとの指定等）は避ける。文言の軽微な言い回し修正のたびに機械的に壊れる一方、検出したい不具合（要素の欠落・大きな誤字）を検出する目的なら、見出しの一部や`role`・`aria-label`ベースのクエリで足りることが多い。

## テストの責務境界とケースの表現

- 子コンポーネントも内部協調オブジェクトの一種であり、原則モックしない。子をモックする場合でも、親が子の表示・非表示や個数を切り替える条件分岐があるなら、その分岐自体を検証するテスト（モックされた子が存在しないことを確認する等）を別途残す
- 呼び出し先（子コンポーネント・協調オブジェクト）が既に検証している内容を、呼び出し元のテストで再確認しない。呼び出し元は「正しい子に正しい値を渡しているか」「呼び出し元自身の責務（分岐・状態遷移等）」のみを検証する
- 同じセットアップから検証できる小さなバリエーションが複数ある場合：
  - 各バリエーションが独立していれば`it.each`/`describe.each`でデータ駆動にする
  - 前のバリエーションの結果が次の前提になる一連の操作シーケンスなら、無理に分割せず1つの`it`にまとめる
  - 複数のテストで共通するセットアップ（モックの設定等）は`beforeEach`に外出しする

## AAAパターン

- Arrange：`const`変数や`beforeEach`でセットアップする
- Act：SUTの呼び出し結果を変数に代入する
- Assert：`expect`と適切なマッチャーで検証する

## 非同期モックの解決タイミングを後から制御する

`mockImplementation`等で返すPromiseの resolve/reject を、テスト内の後続処理から任意のタイミングで呼び出したい場合、そのコールバックを`let`変数に代入して後で呼び出す書き方をしない。TypeScriptの制御フロー解析は、ネストしたクロージャ内でのみ再代入される`let`変数を後続の参照時に誤って`never`型へ絞り込むことがあり、意図しない型エラーになる。

代わりにオブジェクトのプロパティとして保持する。

```ts
// 避ける：後続の呼び出しでTSに`never`型へ誤って絞り込まれることがある
let resolveFirst: (() => void) | null = null

// 推奨：オブジェクトのプロパティ経由で保持する
const firstCall: { resolve: (() => void) | null } = { resolve: null }
vi.spyOn(target, 'method').mockImplementation(() => new Promise((resolve) => {
  firstCall.resolve = () => resolve(undefined)
}))
// ...
firstCall.resolve?.()
```
