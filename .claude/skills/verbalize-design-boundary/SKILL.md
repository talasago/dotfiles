# verbalize-design-boundary

`$ARGUMENTS` の設計判断について、ユーザーが自分の言葉で「なぜそこで切ったか」「ほかの置き方をなぜ退けたか」を言えるようにする。目的は言語化の練習と、職歴で語れる設計判断（背景→判断→トレードオフ→結果）の材料づくり。

AI は判断の中身を書かない。AI が理由や代替案を出すと、それはユーザーの言語化ではなくなるため。

## 進め方

対象のコードは読んでよい（質問を具体的にするため）。ただし読んだ内容から判断や理由を推測して提示しない。

以下の項目を、1ターンに1〜2問ずつ質問する。答えが曖昧なら、どこが曖昧かだけを指摘して聞き直す。

1. **背景**：何を解決したかったか。どんな制約があったか
2. **境界**：責務をどこで切ったか。それぞれのモジュールは何を知っていて、何を知らないか
3. **退けた案**：ほかにどんな置き方を考えたか。それをなぜ退けたか（1案も無ければ、無かったことをそのまま記録する。AI から案を出さない）
4. **トレードオフ**：この切り方で何を得て、何を諦めたか
5. **変更への強さ**：どんな変更が来たら、この境界が効くか／崩れるか
6. **結果**（分かっていれば）：その後どうだったか

抜けの指摘は「〇〇についてはまだ触れていない」の形で、項目名だけを示す。

## 出力

全項目を聞き終えたら、ユーザーの言葉をそのまま使って設計メモの形に並べ、チャットに出力する。言い換え・補足・要約はしない。

```markdown
# 設計メモ：〇〇
- 印：境界 / 非機能（触れたものに付ける）
## 背景
## 判断（境界）
## 退けた案と理由
## トレードオフ
## 変更への強さ
## 結果
```

置き場所（ADR・設計メモ等）はユーザーが決める。
